制定日時: 2026年10月27日 18:00  
対象領域: rpg_simple_engine プロジェクトにおける全開発・リファクタリング作業

## 第0条：コミュニケーションおよび作業承認ステップ

認識の齟齬、予期せぬ仕様破壊、およびAIの暴走を防ぐため、以下の対話プロセスを義務付けます。

1. **事前確認の徹底（推測の禁止）:**
   - 既存仕様やロジックを破壊する懸念がある場合、または仕様定義が不足・曖昧である場合は、推測に基づく実装を禁止します。ファイル変更を伴う設計時は、必ず事前に対象ディレクトリの物理構造と実際の参照経路（ロード元）を静的コマンドで特定・提示し、事実が確定するまでコード作成に着手しません。客観的事実とリスクを提示し、ユーザーへ判断を仰ぎます。
   - 単体テスト（Gate 2）作成時におけるテストデータの推測・仮定を禁止します。マスターデータ（ITEM_DB等）に実在するキー、または実機バックアップセーブデータの確定パラメータのみを入力値として採用し、架空のアイテムIDやステータス境界外の値をコードへ混入させてはなりません。
   - リファクタリング対象外の既存ロジック、コンストラクタ、既存メソッドを AI 側が推測で書き直す行為、または旧リビジョンのコードへ巻き戻す行為を禁止する。差分は改変対象のブロック（関数・メソッド単位）に厳密に局所化し、差分確認（git diff）にて対象外コードの混入がないことを機械的に検証しなければならない   
2. **承認ゲート（合意後のコード出力）:**
   - 方針・設計案を提示した段階で必ず停止します。ユーザーからの明確な「承認」「了解」等の合意を得るまで、実装コードや更新コマンドの出力を開始しません。
3. **回答トーンの統制:**
   - すべての対話は「です・ます調」の客観的アナリストとして記述します。感情的な修飾語やお世辞、命令口調は一切排除します。
4. **構造変化の明示的説明義務:**
   - 委譲およびリファクタリング作業時、AIはコードを提示する前に、必ず「旧実装（Before）の動作と問題点」および「新実装（After）による責務の分離理由」を非プログラマにも理解できる平易な言葉で対比説明しなければなりません。運用者がその構造変化を理解し、合意した場合にのみ作業の進行（承認）を認めます。

## 第1条：主目的および品質優先順位（目的ヒエラルキー）

本プロジェクトの最優先事項は、スパゲッティ状態にあるモジュール間の密結合を断ち切り、将来の機能追加および保守に耐えうる「データ駆動型アーキテクチャ」への安全な移行を達成することです。形式的な構文ルールが本質的な設計品質を阻害してはなりません。

1. **品質判断の優先順位（Tier原則）:**
   - **最優先（Tier 1）: 疎結合化と単一責任の原則**
     - モジュール間の相互参照・内部変数直弄りを排除し、インターフェースを明確化すること。
   - **次点（Tier 2）: 完全ヘッドレス化とポータビリティ**
     - Core層をブラウザAPIおよびグローバル状態から物理的に切り離すこと。
   - **下位（Tier 3）: 構文健全性とフェイルファスト**
     - 禁止演算子の排除および型検証の徹底（※Tier 1やTier 2の可読性・構造を損なわない範囲で適用）。

## 第2条：環境保全およびステージング隔離

1. **クラウド同期の停止確認:**
   - ファイル操作を伴う作業の直前に、Google Drive 等の同期が一時停止されていることを確認します。
2. **作業ツリーの健全性担保:**
   - コマンド実行前に `git status` を確認し、作業ツリーがクリーンな状態であることを確認します。
3. **本番環境の事前静的確認（ステージング着手前）:**
   - ステージング環境の作成およびコード提示を行う前に、必ず本番側の対象ディレクトリ構造、既存同名ファイルの有無、および依存先モジュールの実在パスを PowerShell コマンド（`Test-Path`, `Get-ChildItem` 等）で静的に特定・提示します。
   - 本番の物理構造の事実が確定するまで、ステージングディレクトリの生成およびコード提示を開始しません。
4. **ステージング・ミラー構造の原則:**
   - **ミラー構造の厳格再現:**
     新規作成および変更ファイルの一時出力先は、事前確認で確定した本番環境と同一の相対パス関係を再現したミラー構造（`./ai_staging/js/engine/...` 等）とします。
   - **ディレクトリ生成の自動化:**
     ステージング内のディレクトリ作成は手動操作を禁止し、AIが提示する PowerShell コマンド（`New-Item -ItemType Directory -Force`）により一括自動生成します。
   - **本番隔離の徹底:**
     Gate 1 および Gate 2 を完全に通過するまで、本番コード（`./js/` 等）への直接配置、直接編集、および部分上書きを一切禁止します。
   - **依存関係の自動ミラーリング（必須）:**
     `ai_staging` 内で単体テスト（Gate 2）を実行する際は、ESM 相対モジュール未解決エラー（`ERR_MODULE_NOT_FOUND`）を防止するため、テスト実行前に必ず以下のコマンドを実行して依存ツリーを自動複製しなければなりません。手動でのファイルコピー、および推測に基づく個別配置は禁止します。
     ```powershell
     node tools/prepare_staging.mjs <検証対象テストコード等のパス>
     ```
     ※ 本スクリプトは `ai_staging` 側の既存編集ファイルを自動保護（スキップ）し、未配置の依存ファイルのみを複製します。
   - **昇格時スコープ防護と逆流抑止:**
     Gate 2 通過後に本番環境（`./js/` 等）へ反映する際は、今回のタスクで改変・新規作成したファイルのみを個別に指定してコピー（昇格）します。自動ミラーリングによって一時複製された依存ファイルを本番ツリーへ逆流・上書きすることは厳禁とします。
   - **検証完了後の完全破棄:**
     Gate 3（実機検証）の完了後、またはコミット直前には必ず `Remove-Item -Recurse -Force ai_staging` を実行して一時環境を完全に破棄し、作業ツリーの汚染を防止します。
     
5. **コード提示および生成手段の統制:**
   - シェルの入力バッファ上限による文字欠損やエスケープ干渉を防ぐため、コンソールへの長大文字列の直接入力（Base64 を含む `node -e` 等）によるファイル出力を禁止します。

   - AIは完全なコードブロックを提示し、ユーザーがエディタ等を介して所定のステージングパスへ直接保存する運用を標準とします。
6. **本番環境への昇格およびクリーンアップ:**
   - ステージング環境下で Gate 1（静的検証）および Gate 2（単体テスト）を通過した段階でのみ、ステージングから本番ディレクトリへの昇格（配置）を許可します。
   - 本番への反映は、PowerShell の `New-Item`（ディレクトリ未作成時の確保）および `Copy-Item` を用いた確定コマンドによって実行します。
   - 本番配置後のファイナル検証（全ゲート再実行）および Git コミットが完了した段階で、`./ai_staging/` 配下の作業ファイルを即座に全削除し、作業ツリーをクリーンな状態に戻します。
7. **実行環境およびエンコーディング制約:**
   - 本プロジェクトの実行シェルは Windows PowerShell に限定します。bash/Unix 固有コマンド（`grep`, `cat`, `ls` 等）の提示を禁止し、PowerShell 構文または Node.js 実行コマンドのみを提示します。
   - プロジェクト内の全ファイルは UTF-8（BOMなし）を厳格に維持します。
   - ファイル内容の確認時は、PowerShell 標準の `Get-Content` 単体実行を禁止し、`-Encoding utf8` の明示または Node.js（`fs.readFileSync`）経由での出力を義務付けます。
   - 既存 JSON のスキーマ拡張等に伴うファイル更新時は、ヒアドキュメントによる全文上書きを禁止し、Node.js スクリプトによる差分プロパティのマージ処理によって既存値を保護します。

## 第3条：設計原則およびコード生成規約

AIが出力するコードは、以下の規約をすべて満たさなければなりません。

1. **疎結合・直接参照禁止（Tier 1）:**
   - モジュール同士が相手のインスタンスや内部変数を直接読み書きすることを禁止します。
   - モジュール間のデータ受け渡しは「純粋関数の引数・戻り値」または「イベント通知（EventBus等）」経由に限定します。
2. **完全コード提示の義務:**
   - `// ... 既存のコード ...` などの省略表記を一切禁止し、先頭から末尾まで完全なプレーンテキストで提示します。
3. **完全ヘッドレス原則（Core層限定 / Tier 2）:**
   - `js/engine/` 配下のファイルでは、`window`, `document`, `HTMLCanvasElement`, `AudioContext`, `localStorage` 等のブラウザAPIの直接参照を禁止します。
4. **一方向依存の徹底:**
   - `js/engine/`（Core）から `js/drivers/`（Driver）への `import` を禁止します。
5. **構文健全性とフェイルファスト（Core層限定 / Tier 3）:**
   - `js/engine/` 配下において、論理和（`||`）、三項演算子（`?:`）、Null合体演算子（`??`）を排除し、型検証を伴う明示的な `if`/`else` 分岐を使用します。
   - 不正な引数・境界値に対してはサイレントフェイルを行わず、即座に例外（エラー）をスローします。

## 第4条：3段階検証ゲート（DoD: Definition of Done）

本番配置および Git コミットは、以下の3ゲートをすべて通過した段階でのみ実施します。

```text
[ コード提示（ステージング領域へ出力） ]
                  │
                  ▼
[ Gate 1: 静的構文・境界検証 ] ── 違反 ──> 是正コードの再提示
                  │ 合格
                  ▼
[ Gate 2: ヘッドレス単体機能テスト ] ── 失敗 ──> 是正コードの再提示
                  │ 合格
                  ▼
[ 本番環境への昇格（Copy-Item による配置）]
                  │
                  ▼
[ ファイナル検証: 本番ツリーに対する一括再検証 ]
  ├─ Gate 1: 本番ファイルに対する静的・境界スキャン
  ├─ Gate 2: 本番ファイルを参照する単体テストの実行
  └─ Gate 3: 実機・結合検証（委譲ステップ時のみ）
                  │
                  ├─ エラー検出 ──> 即時ロールバック（第5条: ai_staging削除および個別ファイル復旧）
                  │ 合格
[ Gitコミット・stagingクリーンアップ（1ステップ完了）]
```

- **Gate 1（静的構文・境界検証）**: 検証スクリプト（tools/verify_gate1.mjs）により、Node.js構文チェック、Core層での禁止演算子スキャン、ヘッドレス境界（ブラウザAPI）スキャン、および参照整合性の確認を通過すること。
- **Gate 2（ヘッドレス単体機能テスト）**: 単体テストランナー（tools/test_*.mjs）により、対象モジュール（ステージング時および本番昇格後）に対する正常系・異常系テストが Exit Code 0 でパスすること。
- **Gate 3（結合・実機動作検証）**: 既存コードからの委譲ステップ時、本番配置後にブラウザ上で指定のアクションを実行し、F12開発者ツールのコンソールエラーが0件であることを確認すること（※新規作成ステップでは委譲接続が存在しないためスキップ）。
- **ファイナル検証（DoD最終確認）**: コミット直前に本番ツリーを対象として Gate 1、Gate 2、（必要に応じて Gate 3）を連続実行し、全件合格を確認すること。

## 第5条：即時ロールバック（フェイルセーフ）

検証ゲートで失敗した場合、作業ツリーの保全を最優先とします。

1. **現場での継ぎ接ぎ修正の禁止:**
   - 失敗した中間状態に対して小手先の修正を重ねることを禁止します。
2. **破壊的ロールバックコマンドの提示禁止:**
   - 未追跡のバックアップファイルやドキュメントを永久消失させるリスクを排除するため、リポジトリ全域を対象とする破壊的コマンド（`git reset --hard HEAD`, `git clean -fd` 等）の出力を一切禁止します。
3. **安全な切り戻し手順の徹底:**
   - 使い捨て領域である `./ai_staging/` は即座に全削除（`Remove-Item -Recurse -Force ai_staging`）します。
   - 本番ツリーの追跡ファイルに意図しない変更が発生した場合は、対象パスを明示した個別チェックアウト（`git checkout -- <対象ファイルパス>`）のみを提示・実行します。
   - 未追跡ファイルの確認が必要な場合は、必ずドライラン（`git clean -nd`）で影響範囲を特定・提示した上で、ユーザーの個別判断を仰ぎます。
4. **原因分析と再提案:**
   - エラーログを客観的に精査し、修正方針を再提示した上で、ユーザーの承認を得てから再試行します。

## 第6条：コンテキスト保全およびセッション境界

AIのコンテキスト容量枯渇による誤作動・ハルシネーションを物理的に排除します。

1. **セッション単一責務の原則（使い捨てセッション）:**
   - 1つのチャットセッションで扱う作業は「Gate 3通過およびGitコミット完了」の1ステップまでとします。
   - ステップ完了後はセッションを終了（リセット）し、過去ログの肥大化によるコンテキスト汚染を防止します。
2. **外部台帳（progress.md）による状態の引継ぎ:**
   - 会話履歴の記憶に依存せず、現在の完了ステップ、ファイル構成サマリー、次のタスクのみを記録した外部台帳ファイル（`progress.md`）を常に最新化できるように準備します。外部台帳ファイルの決定及びgitはユーザーに依頼すること。
   - 新規セッション開始時は、この台帳ファイルと直近の変更対象ファイルのみを入力情報とします。
3. **入力情報の最小化（スコープ外コードの遮断）:**
   - プロジェクト全体のソースコードや無関係なモジュールの一括入力を禁止します。作業対象となる最小限のファイルまたはインターフェース仕様のみをコンテキストに提供します。
4. **委譲作業における探査セッションの分離:**
   - 既存コードの修正・委譲を伴うステップでは、実装セッションへの巨大なレガシーファイルの直接入力を禁止します。必ず事前の「探査セッション（コード変更を行わず該当箇所の抽出のみを行う使い捨てチャット）」を経由してください。実装セッションへの入力は、探査フェーズで静的に洗い出した「最小コードブロック（10〜20行）」、「対象ブロックがアクセスしている外部変数・プロパティの一覧」、および「そのコードが何をしているかの平易な解説（3行以内）」の3点のみとします。
