制定日時: 2026年10月27日 18:00  
対象領域: rpg\_simple\_engine プロジェクトにおける全開発・リファクタリング作業

## 第0条：コミュニケーションおよび作業承認ステップ

認識の齟齬、予期せぬ仕様破壊、およびAIの暴走を防ぐため、以下の対話プロセスを義務付けます。

1. **事前確認の徹底（推測の禁止）:**  
   - 既存仕様やロジックを破壊する懸念がある場合、または仕様定義が不足・曖昧である場合は、推測に基づく実装を禁止します。ファイル変更を伴う設計時は、必ず事前に対象ディレクトリの物理構造と実際の参照経路（ロード元）を静的コマンドで特定・提示し、事実が確定するまでコード作成に着手しません。客観的事実とリスクを提示し、ユーザーへ判断を仰ぎます。  
   -・ 単体テスト（Gate 2）作成時におけるテストデータの推測・仮定を禁止します。
   ・マスターデータ（ITEM\_DB等）に実在するキー、または実機バックアップセーブデータの確定パラメータのみを入力値として採用し、架空のアイテムIDやステータス境界外の値をコードへ混入させてはなりません。
   ・少なくとも1つ以上の異常系・境界値（例: 条件不一致でfalseを返す、例外を投げる等）のテストケースを必須とする  
   ・既存累積テストからの既存アサーションの削除・無効化・期待値の引き下げを厳禁とする

   - リファクタリング対象外の既存ロジック、コンストラクタ、既存メソッドを AI 側が推測で書き直す行為、または旧リビジョンのコードへ巻き戻す行為を禁止する。差分は改変対象のブロック（関数・メソッド単位）に厳密に局所化し、差分確認（git diff）にて対象外コードの混入がないことを機械的に検証しなければならない  
2. **承認ゲート（合意後のコード出力）:**  
   - 方針・設計案を提示した段階で必ず停止します。ユーザーからの明確な「承認」「了解」等の合意を得るまで、実装コードや更新コマンドの出力を開始しません。  
3. **回答トーンの統制:**  
   - すべての対話は「です・ます調」の客観的アナリストとして記述します。感情的な修飾語やお世辞、命令口調は一切排除します。  
4. **構造変化の明示的説明義務:**  
   - 委譲およびリファクタリング作業時、AIはコードを提示する前に、必ず「旧実装（Before）の動作と問題点」および「新実装（After）による責務の分離理由」を非プログラマにも理解できる平易な言葉で対比説明しなければなりません。運用者がその構造変化を理解し、合意した場合にのみ作業の進行（承認）を認めます。

## 第1条：主目的および品質優先順位（目的ヒエラルキー）

本プロジェクトの最優先事項は、スパゲッティ状態にあるモジュール間の密結合を断ち切り、将来の機能追加および保守に耐えうる「データ駆動型アーキテクチャ」への安全な移行を達成することです。形式的な構文ルールが本質的な設計品質を阻害してはなりません。

1. **品質判断の優先順位（Tier原則）:**  
   - **最優先（Tier 1）: 疎結合化と単一責任の原則**  
     - モジュール間の相互参照・内部変数直弄りを排除し、インターフェースを明確化すること。  
   - **次点（Tier 2）: 完全ヘッドレス化とポータビリティ**  
     - Core層をブラウザAPIおよびグローバル状態から物理的に切り離すこと。  
   - **下位（Tier 3）: 構文健全性とフェイルファスト**  
     - 禁止演算子の排除および型検証の徹底（※Tier 1やTier 2の可読性・構造を損なわない範囲で適用）。

## 第2条：環境保全およびステージング隔離

1. **クラウド同期の停止確認:**

   - ファイル操作を伴う作業の直前に、Google Drive 等の同期が一時停止されていることを確認します。  
2. **作業ツリーの健全性担保:**

   - コマンド実行前に `git status` を確認し、作業ツリーがクリーンな状態であることを確認します。  
3. **本番環境の事前静的確認（ステージング着手前）:**

   - ステージング環境の作成およびコード提示を行う前に、必ず本番側の対象ディレクトリ構造、既存同名ファイルの有無、および依存先モジュールの実在パスを PowerShell コマンド（`Test-Path`, `Get-ChildItem` 等）で静的に特定・提示します。  
   - 本番の物理構造の事実が確定するまで、ステージングディレクトリの生成およびコード提示を開始しません。  
4. **Gitブランチによる作業隔離およびマージ前実機検証の原則:**
   - **ブランチ隔離の徹底:** 新規作成および既存コードの改変は、本番線（`main` ブランチ）上では一切行わず、必ずタスク専用の作業ブランチ（`git switch -c step/xxx`）を新設して行います。`ai_staging` ディレクトリ等の物理的なファイル複製は廃止します。
   - **ブランチ内直接配置と累積検証:** 作業ブランチ内では直接対象パス（`./js/...` 等）にコードを配置し、Gate 1（静的構文検証）および Gate 2（ヘッドレス累積テスト: `test_headless_run.mjs`）を実行します。
   - **サブステップのローカルコミット:** 1つのサブステップ（例: Pre-4a）ごとに Gate 1 および Gate 2 の合格（Exit Code 0）を確認した段階で、作業ブランチ内にて即時コミットします。この段階ではブラウザ実機検証（Gate 3）はスキップ可能です。
   - **親ブランチ（main）合流時の実機検証義務（Gate 3）:** 作業ブランチの全サブタスクが完了し、`main` ブランチへマージする直前には、必ずブラウザ実機にて指定の動作確認を行い、F12コンソールのエラーが0件であることを確認しなければなりません。Gate 3 未実施のブランチを `main` へ合流させることは厳禁とします。
   - **破綻時の即時破棄:** 作業ブランチ内で解決不能なデグレや設計破綻が発生した場合は、`git switch main` で本線へ復帰し、該当ブランチを強制削除（`git branch -D step/xxx`）することで、本線環境を完全な健全状態へ復元します。

5. **コード提示および生成手段の統制:**

   - シェルの入力バッファ上限による文字欠損やエスケープ干渉を防ぐため、コンソールへの長大文字列の直接入力（Base64 を含む `node -e` 等）によるファイル出力を禁止します。

   - AIは完全なコードブロックを提示し、ユーザーがエディタ等を介して所定のステージングパスへ直接保存する運用を標準とします。

6. **実行環境およびエンコーディング制約:**

   - 本プロジェクトの実行シェルは Windows PowerShell に限定します。bash/Unix 固有コマンド（`grep`, `cat`, `ls` 等）の提示を禁止し、PowerShell 構文または Node.js 実行コマンドのみを提示します。  
   - プロジェクト内の全ファイルは UTF-8（BOMなし）を厳格に維持します。  
   - ファイル内容の確認時は、PowerShell 標準の `Get-Content` 単体実行を禁止し、`-Encoding utf8` の明示または Node.js（`fs.readFileSync`）経由での出力を義務付けます。  
   - 既存 JSON のスキーマ拡張等に伴うファイル更新時は、ヒアドキュメントによる全文上書きを禁止し、Node.js スクリプトによる差分プロパティのマージ処理によって既存値を保護します。

## 第3条：設計原則およびコード生成規約

AIが出力するコードは、以下の規約をすべて満たさなければなりません。

1. **疎結合・直接参照禁止（Tier 1）:**  
   - モジュール同士が相手のインスタンスや内部変数を直接読み書きすることを禁止します。  
   - モジュール間のデータ受け渡しは「純粋関数の引数・戻り値」または「イベント通知（EventBus等）」経由に限定します。  
2. **完全コード提示の義務:**  
   - `// ... 既存のコード ...` などの省略表記を一切禁止し、先頭から末尾まで完全なプレーンテキストで提示します。  
3. **完全ヘッドレス原則（Core層限定 / Tier 2）:**  
   - `js/engine/` 配下のファイルでは、`window`, `document`, `HTMLCanvasElement`, `AudioContext`, `localStorage` 等のブラウザAPIの直接参照を禁止します。  
4. **一方向依存の徹底:**  
   - `js/engine/`（Core）から `js/drivers/`（Driver）への `import` を禁止します。  
5. **構文健全性とフェイルファスト（Core層限定 / Tier 3）:**  
   - `js/engine/` 配下において、論理和（`||`）、三項演算子（`?:`）、Null合体演算子（`??`）を排除し、型検証を伴う明示的な `if`/`else` 分岐を使用します。  
   - 不正な引数・境界値に対してはサイレントフェイルを行わず、即座に例外（エラー）をスローします。

## 第4条：標準運用ライフサイクルおよび検証ゲート（DoD）

1. 3段階セッション分離パイプライン（検査の独立性）
AIによる自己欺瞞（自身の実装を通すためのザルテスト作成）を物理的に排除するため、1つのタスクは独立した3つの使い捨てセッションを経て完遂します。

【 セッション1：探査セッション（検察官 / 要件抽出）】
  ・既存コードの解析、外部依存および破壊してはならない仕様・境界値の特定
  ・出力：【テスト仕様書カプセル】（日本語の正常系・異常系テスト条件リスト）
              │
              ▼（仕様書のみを引き継ぎ）
【 セッション2：テスト作成セッション（監査官 / 検査装置製造）】
  ・本体実装は見せず、テスト仕様書のみに基づき厳格な単体テストコードを作成
  ・出力：【テストコード固定カプセル】（tools/test_xxx.mjs の完成コード）
              │
              ▼（テストコードと仕様を引き継ぎ）
【 セッション3：実装セッション（被疑者 / 本体実装・検証・合流）】
  ・テストコードの改変を厳禁とし、テストをGreenにする本体コードのみを実装
  ・Gate 1〜3 を通過させ、本線（main）へ合流

2. 実装セッションの標準運用フロー
実装セッションは、必ず main の健全性確認から開始し、検証ゲートを経て main へ合流・終了するまでの以下の標準サイクルに従って遂行します。

【 1. セッション開始・事前準備 】
[ main ブランチの健全性確認（git status で作業ツリーが Clean であること） ]
      │
      ▼
[ 事前静的確認（対象ファイルの物理構造・参照経路の特定、変更方針の合意） ]
      │
      ▼
[ 作業ブランチの作成・切り替え（git switch -c step/xxx） ]
      │
      ▼
【 2. サブステップ開発サイクル（作業ブランチ内） 】
  [ テストコード配備（セッション2で確定したテストコードを配置・累積テストへ登録） ]
      │
      ▼
  [ 本体コード配置（テストを満たす受け皿・委譲コードの直接反映） ]
      │
      ▼
  [ Gate 1: 静的構文・境界検証（tools/verify_gate1.mjs） ] ── 違反 ──> 是正
      │ 合格
      ▼
  [ Gate 2: ヘッドレス累積テスト（tools/test_headless_run.mjs） ] ── 失敗 ──> 是正（※本体コード側のみ）
      │ 合格
      ▼
  [ サブステップのローカルコミット（git commit） ]
      │
      ├─ 次のサブステップがある場合 ──> 【2】を繰り返し
      │
      ▼ 全サブステップ完了
【 3. 合流前ファイナル検証 】
[ Gate 3: 結合・実機動作検証（ブラウザ実機確認 & F12エラー0件） ]
      │
      ├─ 不合格 ──> ブランチ内で是正、または即時ロールバック（枝の強制破棄）
      │ 合格
      ▼
【 4. 本線合流・セッション終了 】
[ main へ復帰・合流（git switch main && git merge step/xxx） ]
      │
      ▼
[ 作業ブランチの削除（git branch -d step/xxx） ]
      │
      ▼
[ 進捗台帳（progress.md）の更新・コミット ──> セッション終了 ]

3. 各検証ゲートの合格基準（DoD）

- Gate 1（静的構文・境界検証）:
node tools/verify_gate1.mjs を実行し、Node.js構文エラー、Core層での禁止演算子、ブラウザAPI直接参照、およびモジュール参照切れが0件であること。各サブステップのコミット前に必須実行。

- Gate 2（ヘッドレス累積単体テスト）:
node tools/test_headless_run.mjs を実行し、過去の全テスト項目を含めて Exit Code 0 でパスすること。セッション2で確定したテストコードおよび既存テストのアサーション削除・改ざん・期待値引き下げは厳禁（発覚時は即時差し戻し）。各サブステップのコミット前に必須実行。

- Gate 3（結合・実機動作検証）:
全サブステップ完了後、main 合流直前に必須実行。ブラウザ実機にて改変箇所のシナリオを実際に操作し、画面崩れや進行不能がなく、F12開発者ツールのコンソールエラーが0件であることを確認すること。

- ロールバック規程:
各ゲートで解決困難なデグレや設計破綻が発生した場合は、現場での継ぎ接ぎを行わず、git switch main の後に git branch -D step/xxx を実行して作業ブランチを破棄し、セッション開始前の健全状態へ即時復元すること。

## 第5条：即時ロールバック（フェイルセーフ）
検証ゲートで失敗した場合、または予期せぬ不整合・デグレが発生した場合は、作業ツリーの保全および main ブランチの健全性維持を最優先とします。

- 現場での継ぎ接ぎ修正の禁止:
失敗した中間状態や破損したコードに対して小手先の修正を重ねることを禁止します。手戻りが深まる兆候を検知した場合は、即座に当該サブステップまたはブランチ全体の破棄を選択します。

- 破壊的ロールバックコマンドの提示禁止:
未追跡のドキュメントや作業資産を消失させるリスクを排除するため、リポジトリ全域を対象とする無差別な破壊的コマンド（git reset --hard HEAD, git clean -fd 等）の出力を一切禁止します。

- 作業ブランチ単位での完全切り戻し（標準手順）:
作業ブランチ内で修復不能なエラー・設計破綻が生じた場合は、以下の2コマンドのみで作業前のクリーンな状態へ復帰します。

PowerShell
git switch main
git branch -D <作業ブランチ名>

これにより、main の健全な状態を復元し、中途半端な変更ファイルを作業ツリーに残しません。

- サブステップ単位の部分切り戻し（ブランチ内での復旧時）:
直前のサブステップコミットまで戻して作業をやり直す場合は、ブランチ破棄を行わず、対象ファイルのみを明示した個別チェックアウト（git checkout HEAD -- <対象ファイルパス>）を提示・実行します。

- 原因分析と再提案:
切り戻し実行後、失敗時のエラーログおよびテスト結果を客観的に精査し、失敗原因と代替設計案を提示した上で、ユーザーの承認を得てから新しいブランチで再試行します。

## 第6条：コンテキスト保全およびセッション境界

AIのコンテキスト容量枯渇による誤作動・ハルシネーションを物理的に排除します。

1. **セッション単一責務の原則（使い捨てセッション）:**  
   - 1つのチャットセッションで扱う作業は「Gate 3通過およびGitコミット完了」の1ステップまでとします。  
   - ステップ完了後はセッションを終了（リセット）し、過去ログの肥大化によるコンテキスト汚染を防止します。  
2. **外部台帳（progress.md）による状態の引継ぎ:**  
   - 会話履歴の記憶に依存せず、現在の完了ステップ、ファイル構成サマリー、次のタスクのみを記録した外部台帳ファイル（`progress.md`）を常に最新化できるように準備します。外部台帳ファイルの決定及びgitはユーザーに依頼します。  
   - 新規セッション開始時は、この台帳ファイルと直近の変更対象ファイルのみを入力情報とします。  
3. **入力情報の最小化（スコープ外コードの遮断）:**  
   - プロジェクト全体のソースコードや無関係なモジュールの一括入力を禁止します。作業対象となる最小限のファイルまたはインターフェース仕様のみをコンテキストに提供します。  
4. **セッション境界と「引継ぎカプセル」によるコンテキスト遮断:**  
   - 既存コードの改変を伴うタスクでは、巨大なファイルを直接実装環境に持ち込むことを禁止し、第4条に定める各フェーズ（探査・テスト作成・実装）ごとに独立した使い捨てセッションを適用します。  
   - セッション間の情報伝達は、AIが各フェーズ完了時に出力する「定型引継ぎカプセル（要件定義カプセル／テスト仕様カプセル）」の受け渡しのみに限定します。  
   - 実装セッションへの入力は、探査およびテスト作成フェーズで確定した「最小コードブロック」「外部依存一覧」「固定されたテストコード」のみとし、余分な過去ログによるコンテキスト汚染を物理的に遮断します。
